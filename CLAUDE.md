## Project status

Early-stage university project ("Proyecto Final – Taller de Bases de Datos"): a **library management system (Biblioteca)** built by a team of 3. There is no build, lint, or test tooling yet. Current contents:

- `database/db.sql` — creates `biblioteca` and the 6 tables: `bibliotecarios` (app users/roles; `rol` enum administrador/operador/consulta), `alumnos`, `libros`, `ejemplares` (physical copy, `codigo_barras` UNIQUE, `estado` disponible/prestado), `prestamos` (links alumno + ejemplar + bibliotecario; `fecha_devolucion` NULL = still on loan), `auditoria`. Table/column names are Spanish snake_case with `id_<table-singular>` PKs.
- `database/{procedimientos,funciones,triggers,transacciones}.sql`, `diccionario_datos.md` — placeholders (`-- Pendiente` / empty). Per the brief, audit rows are generated by triggers on loan/return; loan/return is the natural explicit transaction.
- `src/main.py` — empty. `docs/documentos.md` — actors (Administrador, Operador, Consultor) and use cases (the source for role permissions); `requirements/procesos.md` and `README.md` are stubs/short.
- `requirements/*.md` — the project brief (in Spanish): decisions, team, requirement checklist, deliverables. Read it before designing anything.

## Requirements that shape the design

These come from the project brief and affect schema and app architecture across multiple files:

- Barcode stored in a column with a `UNIQUE` constraint; app must support lookup by barcode, and a physical scanner must work in the live demo (scanners typically act as keyboard input ending in Enter).
- Users table: id, full name, username, **hashed** password, role, status. Login with real role-based permissions (e.g. administrador / operador / consulta), enforced both in the app and via MySQL users/roles/grants.
- Database objects the app must actually call: at least 1 explicit transaction (`START TRANSACTION`/`COMMIT`/`ROLLBACK`, e.g. a loan or return touching several tables), 3 stored procedures (one with IN params, one with OUT, one that modifies data), 2 stored functions, 2 validation triggers, 2 audit triggers writing to an audit table (table, operation, timestamp, user, old/new data).
- 1–2 reports in the app combining 3+ of: JOIN across 3+ tables, subqueries, aggregation/GROUP BY/HAVING, EXISTS, window functions, CTEs.
- Deliverables include separate SQL scripts: creation (tables), procedures/functions/triggers, and users/roles/permissions, plus ER diagram, relational model, and data dictionary (planned under `docs/`).
